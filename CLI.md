# Aether CLI — feature backlog

Scratch space holds the analysis scripts used while fixing the Mach-O loader and writing `ProcedureDetector`.
Most are throwaway re-implementations of things the CLI should do natively: they take a raw binary path, hand-parse the header, and print what `aether` cannot print today.
Living list. Each entry names its scratch evidence, the proposed CLI surface, and the cost in AetherKit terms, plus a status line where the proposal has partially landed.
Implemented entries are deleted rather than left behind, so the numbering has permanent gaps; entry numbers never shift, which keeps cross-references such as "entry 19" valid across edits.

## Verified CLI surface today

`aether --help` registers seven model groups — `program`, `section`, `segment`, `symbol`, `procedure`, `annotation`, `bookmark` — plus `import`, `inspect`, `addr`, `bytes`, `find`, `hash`, `doctor`, `snapshot` and `changes`; `new` is gone because the project argument is created on demand.
`aether --version` answers `1.0`: the CLI's own `CommandConfiguration.version` is the module constant `cliVersion` in `Sources/Aether.swift`, hand-carried to match `Aether.xcodeproj`'s `MARKETING_VERSION` (the only version declared anywhere in the repo), and `doctor` prints it as `cli=1.0` in its census line. ArgumentParser adds the flag to every command in the stack once any one declares a version, so every subcommand accepts `--version` (see gotchas).
Every group carries `fetch` / `count` / `delete`; every group except `program` also carries `insert`, `procedure` additionally carries `detect` and `symbol` additionally carries `raw`.
No group sets `defaultSubcommand`, so the subcommand has to be spelled out. The project is a positional `<project>` argument, and because option groups come first in the parse order it is always the first positional — `aether symbol fetch D`, `aether symbol insert D bin name address`.
`Sources/Fetch<T>.swift` is the read-side machinery: a `FetchableModel` protocol with `plural`, `fields()`, `describe()`, an associated `FetchOptions` defaulting to `EmptyOptions` (`Sources/Utilities.swift`), `static var subcommands`, the cascade hook `static cascade(of:in:)` — which asks what else goes when a selected row goes, is empty by default, and is overridden by `program`, `segment`, `symbol` and `procedure` — the `--demangle` hooks `demanglable` / `mangledName` / `row(applying:)` — each defaulted so that only `symbol` and `procedure` opt in — and `static func apply(_:to:in:)` — which now also takes the `ModelContext` and may `throw`, because a name or a file offset has to be looked up in the document before it becomes a comparable address. It also holds `CascadeReport`, the same-shape accumulator both `delete` and `import --replace` print from: `taken` for rows a `deleteRule: .cascade` relationship removes, `left` for rows that survive still pointing at a deleted one, and `describe()` rendering both in `schemaOrder` rather than dictionary order. `fields()` is the row as ordered `key` / `value` / `text` triples (`Sources/Row.swift`: `RowField` plus the `field` / `head` / `at` factories) and `describe()` is a protocol-extension default that hands `fields()` to `render(_:)`, which joins the `text` of each, so a field added to a row lands in both renderings at once — the seven rows diffed byte-identical against the pre-refactor capture, apart from the control-character escaping described under gotchas.
`CountCommand` and `DeleteCommand` take the same `Model.FetchOptions`, so every filter below is also a filter on `count` and on `delete` — and `DeleteCommand` now takes the census *before* it deletes, so its line is `Deleted N <plural>` plus, when anything else moved, ` — the cascade takes …; left behind …` (exact shapes under gotchas).
`Sources/Insert<T>.swift` is the write side: an `InsertableModel` protocol — which now refines `FetchableModel`, since everything insertable is fetchable — with `singular` and `init(options:using modelContext:) async throws`; `InsertCommand` builds the model, inserts it, skips `save()` under `--dry-run`, and prints `Inserted <describe()>`.
`Sources/Utilities.swift` holds `EmptyOptions`, the `hex(_:)' helper over `some BinaryInteger`, the `InsertError` enum (`unknownBinary` / `unknownSegment` / `unknownSymbol` / `duplicate`), the `AddressArgument` value type with its `AddressError` enum, and `requireBinary(named:in:)` / `requireProgram(named:in:)`, which resolve the program an insert or an address lookup operates on; the `--section` filter added `SectionError` with `filterSection(_:named:in:)`, which turns a section name into the range of addresses it covers, and `--demangle` added `DemangleError` with `demangledNames(_:)`, which batches a page of names through the toolchain's demanglers.
`Sources/AetherKit+.swift` exists only to add `@retroactive ExpressibleByArgument` for `AnnotationKind`, `SymbolKind`, `SymbolType`, `SymbolBinding`, `BinaryFormat`, `Endianness` and `Architecture`; without it none of those enums parse as a CLI value.
`AetherOptions` (`Sources/Aether.swift`) carries a required positional `<project>` plus two bare flags, `--dry-run` and `--existing`; `import`, `delete`, `insert` and `procedure detect` all guard `save()`.
The store is opened per command by `AetherOptions.modelContainer()`, which throws a `StoreError` — `missing(url:)` when `--existing` meets a nonexistent path, `unopened(url:reason:)` when a store cannot be migrated — instead of force-unwrapping; `mainContext()` (a `@MainActor` pass through `ModelContainer.mainContext`) and `backgroundContext()` (a plain `ModelContext`) both go through it, and nothing is cached in the group because a `ParsableArguments` struct has to stay `Decodable`. Opening still creates the `.aetherproj` directory (missing parents included) when it does not exist — the behaviour `new` used to perform by hand — and `--existing` is the only opt-out.
The schema just changed under the CLI: `BinaryFormat`, `Endianness` and `Architecture` are now `Int`-backed enums, and `SymbolKind` / `SymbolType` / `SymbolBinding` gained `CaseIterable, Sendable`.
Every row is one `key=value` line — greppable, and the shape entry 7's `--json` renders from the same fields:
- `program`: `thin_test machO arm64 little 64-bit 51480 bytes sha256=BBE70CFB… base=100000000 entry=1000006E8 stack=0 file=<path> segments=5 sections=11 symbols=42 procedures=14 references=0 annotations=0 bookmarks=0` — the three header enums print as case names, not numbers, and `sha256=` is the whole-file digest entry 25 landed, elided here for readability.
- `segment`: `MYSEG @1000FE000 size=4096 file=0+1000 prot=rw- maxprot=7 initprot=3 sections=1 program=thin_test`.
- `section`: `MYSEG,MYSEC @1000FE000 size=32 offset=A align=4 flags=1 executable=false zerofill=true code=false segment=MYSEG program=thin_test`.
- `symbol`: `my_sym @100001634 size=1 kind=function type=u64 binding=global import=false export=false identifier=my_sym value= program=thin_test`.
- `procedure`: `name @addr size= frame= thunk= leaf= demangled= blocks= callers= callees=` plus inline `arguments=[name: type reg|sp+n]` and `locals=[name: type sp+n:size]`.
- `annotation`: `entry point @1000006E8 kind=trailing program=thin_test`; `bookmark`: `main @1000006E8 created=2026-11-03 20:59:55 +0000 summary=program entry program=thin_test`.
Hex is upper-case through one `hex(_:) helper`, and `persistentModelID` is printed nowhere at all: `import` ends with the program's own `describe()` row, or with the same row as a JSON object under `--json`.
Every group now sorts: children by address (`procedure` by `symbol.address`), `program` by name.
`fetch` pages by **100 rows by default** and takes `--limit` / `--offset` / `--all` (`--all` wins over an explicit `--limit`, `--limit 0` prints only the total), then prints `Showing 100 (1-100) of 15052 symbols:` — the range is the 1-based inclusive span of the rows this page printed — followed by `… 14952 more — --all for every row, --offset 100 for the next page` whenever rows remain, the total being a second `fetchCount` taken before the page is applied. The default page is text-mode only (`--json` takes just what was typed), and `count` has no page options at all — it rejects `--limit` at exit 64 — so it is always the whole census.
`import` takes `--no-analyze` (skip the procedure-detection pass), `--quiet` (drop the loader's narration) and `--replace` (first delete every stored program whose name equals the imported file's last path component, so re-parsing a program does not leave a second copy of it in the document). The replacement is reported on its own line, in exactly the shape `program delete` prints — `Deleted 1 programs — the cascade takes 5 segments, 11 sections, 42 symbols, 14 procedures` — and that line appears only once the parse has succeeded: the command keeps its single `save()` at the end, so a file the loader rejects prints nothing and leaves the old program and its rows intact (see gotchas). The library side moved with the entry: `MachOLoader.machO(for:analyze:)` and `load(_:analyze:)` return `MachOLoadReport(log:procedures:)` instead of printing, so only the CLI decides what reaches stdout; the app's `try await MachOLoader.load(binary)` call site discards the report and compiles unchanged.
`inspect` is the one command that takes no `<project>`: it builds a `BinaryModel` from a raw executable path, parses it through `MachOLoader.load(_:analyze:)` against an in-memory `ModelConfiguration(schema: .project, isStoredInMemoryOnly: true)`, and prints `program.describe()`, then every segment and section row through the same `describe()` used by `fetch`, then a symbol census over `kind` / `binding` / `type` plus a string-row count. Detection is opt-in there — `--analyze` — where `import` runs it by default; `--log` prints the report narration.
`addr <project> [address] [--binary <name>]` prints one line for one place: `@1000006E8 off=6E8 program=thin_test segment=__TEXT prot=r-x section=__TEXT,__text symbol=_main @1000006E8+294 procedure=_main`, with `off=none` / `segment=none` / `section=none` / `symbol=none` / `procedure=none` when nothing covers the address. It takes `--binary` because a document holding several programs cannot say which one an address belongs to.
Address arguments are one `AddressArgument` value type (`Sources/Utilities.swift`) shared by every address the CLI takes — `--address` on all six groups and the positional address of `symbol` / `section` / `segment` / `annotation` / `bookmark insert`, and of `bytes` and `find --pointer-to`: decimal, `0x…`, the `@…` spelling `describe()` prints, `off:<file offset>` (hex or decimal after the prefix) and an exact symbol `name` or `identifier`. A bare all-decimal token is always a virtual address; `0x` with non-hex digits is a typed error rather than a symbol lookup.
`bytes <project> <address> [--binary <name>] [--length <n>] [--as <kind>]` reads the file at that place. By default it prints 16-byte hexdump rows with an ASCII gutter (64 bytes, max 4096); `--as u8 u16 u32 u64 f32 f64 ptr cstr wstr` prints one line per value (max 256), each starting where the previous one ended, so a `cstr` consumes its terminator and `--length 2` reads the next string too. The first line is the same `key=value` header `addr` prints, so the three commands agree about where they are; `bytes=8 asked=64` marks a run truncated by the end of the file. One `--length` covers both modes — bytes for the dump, values for a typed read — so there is no invalid option combination.
`find <project> [--binary <name>] [--bytes <hex>] [--text <s>] [--pointer-to <address>] [--limit <n>] [--all]` searches the file bytes. `--bytes` is a byte pattern with `??` for any byte (`DE??00`, max 4096), `--text` is a literal matched as its UTF-8 bytes, and `--pointer-to` searches for the address encoded the way the file spells addresses, so it takes the whole `AddressArgument` vocabulary — `--pointer-to _main` works. Any number of the three may run in one invocation, each printing its own `search=… pattern=… program=…` line and a `Showing N (…) of M hits:` line, then one row per hit: `off=6E8 @1000006E8 segment=__TEXT section=__TEXT,__text` (`aligned=true|false` added on pointer rows). All three reduce to one matcher over a needle of bytes, some of which do not care what they match; `--limit 0` counts without printing and `--all` prints every hit.
`hash <project> [--binary <name>] [--scope <file|body|layout>] [--digest-only]` digests programs, printing one `program=<name> scope=<kind> input=<bytes> md5=<…> sha256=<…>` row per program per scope (`input=` says how many bytes the digest covered). `file` is `BinaryModel.data` exactly as stored; `body` concatenates the sections in address order, taking each section's bytes through its own segment's `fileOffset` / `fileSize` the way `bytes` does; `layout` digests a text rendering of the section rows — address, segment name, section name, size, `flags`, `alignment` — rather than file bytes, so it is the shape view rather than the content view. `--digest-only` drops the two header lines and prints bare sha256s, which is what lets `for p in *.aetherproj; do aether hash "$p" --scope file --digest-only; done | sort | uniq -d` name the duplicate stores. The computation lives on `BinaryModel` in AetherKit (`digestInput(_:)`, `hash(_:of:)` over the nested `DigestAlgorithm`, and `sha256` for `describe()`), so `program fetch` and `hash` cannot drift apart.
`doctor <project> [--json] [--strict]` diagnoses the store rather than a slice of it. First line is the census — `project=<abs path> store=<abs path>/StoreContent cli=1.0 programs=1 segments=5 sections=11 symbols=44 procedures=14 annotations=1 bookmarks=2`, one `fetchCount` per model type plus `cli=` from `cliVersion` — then per program an identity line (`thin_test: format=machO endian=little architecture=arm64 bits=64 bytes=51480 base=100000000 entry=1000006E8 file=<path>`, `file=<not read from disk>` when `fileURL` is nil), a containment line (`thin_test: 44 symbols over 11 sections — 30 inside a section, 13 at address 0, 1 outside one`), up to 5 offending rows under `outside one — a row with bytes no section accounts for:` and `  … and N more` past that, then a histogram line — `thin_test: kinds unknown:15 function:14 data:15 — types unknown:29 ascii:1 function:14 — bindings undefined:2 local:27 global:2 external:13` — naming every `SymbolKind` / `SymbolType` / `SymbolBinding` case that has rows, in case order, and one more line for a program whose every row is unknown on both the kind and the type axes. Containment and the histograms are one Swift-side walk over the public `BinaryModel.sections` / `.symbols` relationships plus `section(containing:)`, which no predicate can state, so the distribution costs no extra query. A store with no program prints `the store holds no program — import one before asking anything else of it`; a program with no symbol rows prints its containment line and no histograms. `--strict` turns the report into a gate: exit 1 — printing nothing extra — when any row lies outside every section or any program has every row untyped, while plain `doctor` exits 0 on any store it can open whatever it finds. `--json` prints the census object plus one object per program with `symbols` / `insideSections` / `atZero` / `outsideSections` / `kinds` / `types` / `bindings` / `untyped`, every value a string like everywhere else.
`snapshot <project> [--out <file>]` pins every row of the document — all seven model groups in schema order, nothing filtered — printing `Snapshot 78 rows to .qwen/tmp/snap.json — 1 programs, 5 segments, 11 sections, 44 symbols, 14 procedures, 1 annotations, 2 bookmarks`; the tally reuses `delete`'s plurals, drops kinds with no rows and prints the bare line when the store is empty. Without `--out` the rows go to stdout and the summary is suppressed, so `aether snapshot D > f.json` writes a file `changes` can read — and a redirected run and `--out` are byte-identical, trailing newline included. A row is one JSON object of strings built from the same `fields()` `fetch --json` renders, with a leading `"group"` discriminator and, on `program` rows, no `file` key; two runs over an unmodified store write the same bytes. It takes no page options — a partial record is not a record.
`changes <project> <file> [--limit/--offset/--all] [--fail-changed]` re-reads the store and diffs it against that file, printing one verdict line first — `Differences: 5 of 78 pinned rows — 1 added, 1 removed, 1 renamed, 1 moved, 1 changed`, or `Differences: 0 of 78 pinned rows — the project matches the snapshot` — then one line per difference:
```
changed symbol DAT_100000AEA — size 10 -> 12
moved symbol ___swift_reflection_version @100000AE8 -> @100000AF0
renamed symbol DAT_100000B18 -> my_data @100000B18
removed symbol DAT_100000B20 @100000B20
added symbol my_note @100000AF8
```
Rows cancel on their whole field set first, so the 15052 rows that did not move cost a dictionary lookup and never pair up. What is left pairs inside a group/program/name bucket — a lone `address` difference is `moved`, anything else is `changed` and names every field that differs — and only rows with no counterpart in the other side's bucket are then matched on everything-but-the-name, which is what makes a rename one line rather than a `removed` plus an `added`. The page group is entry 23's, shared with `fetch` (`… 4 more — --all for every difference, --offset 2 for the next page`), and the verdict line is never paged. `--fail-changed` exits 1 through a thrown `ExitCode`, printing nothing extra so the verdict line stays the only thing to read. Neither command takes `--json`.
`--json` is a `@Flag` on every group's `fetch` and `count` and on `insert`, plus `import` and `procedure detect`. `fetch --json` prints a JSON array — `[`, one object per row, one per line, `]`, or bare `[]` when nothing matched — keyed by exactly the names the text rows use (`name` / `address` / `size` / `prot` / `align` / `binding` / `frame` / `arguments` / `text` / `created` / `program` …), and the `Showing N (lo-hi) of M` header and its `… N more` line are suppressed — with them goes the 100-row default page, because an array that stopped early would have nothing to admit it, so `fetch --json` still prints every row unless `--limit` is typed. `count --json` gives `{"plural": "symbols", "count": "44"}`; `insert --json` prints the bare row object with no `Inserted ` prefix; `import --json` prints that object and nothing else — it implies `--quiet` — and the object is byte-identical to `program fetch --json`'s row except that `--replace` appends one `"replaced"` key, and only when that flag was passed (`"replaced": "0"` when nothing matched), so a script that did not ask for a replacement parses exactly what it did before. `procedure detect --json` prints one object per program with the report's own aggregates (`codeSections`, `entryPoints`, `synthesized`, `created`, `total`) instead of the summary sentence; `symbol raw --json` prints one object of counts. `delete` has no `--json`: it reports a count line, which is already one number — now with a ` — <clause>` of cascade counts hanging off it in text, which is prose a script has to split rather than a field (see gotchas).
`--demangle` is a `@Flag` on every group's `fetch` and nowhere else: it changes how a row is printed, so `count` and `delete` reject it (`Error: Unknown option '--demangle'`) and a group whose rows carry no name exits 1 with `Nothing to demangle in sections: these rows carry no symbol name`. `symbol` and `procedure` opt in through `demanglable` / `mangledName` / `row(applying:)`, and the names on a page are batched by `demangledNames(_:)` (`Sources/Utilities.swift`) through `/usr/bin/swift demangle` and `/usr/bin/c++filt`, then looked up per row by mangled name. A `symbol` row gains a trailing `demangled=…` field and a `procedure` row fills its existing `demangled=` column in place, leaving a name the user stored with `procedure insert --demangled` alone. Under `--json` the `demangled` key appears only on rows that got one; text mode adds one census line — `demangled 4 of 6 rows`, or `demangled 0 of 3 rows — neither /usr/bin/swift demangle nor /usr/bin/c++filt recognised these names` when the whole page is a mangling neither tool speaks.
`symbol raw <project> [<the whole symbol filter group>] [--limit/--offset/--all] [--analyze] [--json]` re-parses the program's stored bytes in an in-memory store and diffs the result against the stored symbol rows, writing nothing. `--analyze` decides whether the re-parse runs procedure detection as well as the parse, and it is not cosmetic: the detector appends symbol rows of its own, so parse-only sees 33 rows and 11 stale while `--analyze` sees 42 rows and 2 stale on the same store. Its output is one census line (`thin_test: 33 of 33 re-parsed rows, 44 of 44 stored rows`), one bucket line (`missing 0 stale 11 changed 0`), a line naming the skipped detection pass when that pass was skipped, then three sections — `missing — what a re-parse would add`, `stale — stored rows the current loader no longer produces`, `changed — same address and name, different size/type/value` — each a count line plus `describe()` rows paged by the same `--limit` / `--offset` / `--all` group (`… : 11, showing 2` when capped, and capped at 100 rows by default like `fetch`). Rows are matched on `hex(address):identifier`, which is the store's own `#Unique` identity; the kept/total split in both the census line and the JSON object (`program` / `analyze` / `fresh` / `freshTotal` / `stored` / `storedTotal` / the three buckets) is what stops a clean report under a filter from reading as a clean report about the whole program. It is a subcommand rather than the entry's `--raw` flag because `--raw` in the shared `FetchOptions` group would be accepted by `count` and `delete`, where a scan has no meaning, while `procedure detect` is the existing precedent for a group's extra subcommand — and it still takes the whole filter group, which is how the entry's "`--min-length` belongs to the fresh scan as much as to the stored rows" requirement is met: one Swift-side rule (`SymbolModel.matches(_:address:section:)`) filters both halves, since no descriptor can reach a row that is not in the store.
Helpers still `public` and directly reusable: `BinaryModel.read(at:count:)`, `readString(at:)`, `data(in:)`, `format(hex:)`, `section(containing:)`, `digestInput(_:)` / `hash(_:of:)` / `.sha256`, `SegmentModel.protectionString`, `SectionModel.{isExecutable,isZeroFill,containsCode}`, `SymbolModel.isStringPredicate`, `SymbolModel.displayName`.

### Filters on the wire today

`program`: `--name` (contains), `--format`, `--architecture`, `--endian`.
`segment`: `--binary`, `--name`, `--address`, `--protection` (exact `initProtection`).
`section`: `--binary`, `--segment`, `--name`, `--address`, `--flags` (exact).
`symbol`: `--binary`, `--name`, `--address`, `--kind`, `--type`, `--binding`, `--value` (contains over `stringValue`), `@Flag --imported`, `@Flag --exported`, `--min-length <n>` (decimal, over the stored `size`) and `--section <name>` or `<segment>,<name>` (exact, resolved to the section's address range before the predicate is built; the name errors are under gotchas). Both are also filters on `count`, on `delete`, and on `raw`'s two halves.
`procedure`: `--name` and `--address` through the `symbol` relationship, `--binary`, `@Flag --thunk`, `@Flag --leaf`.
`annotation`: `--text`, `--binary`, `--address`, `--kind`; `bookmark`: `--binary`, `--name`, `--address`, `--summary`.
`--binary` is the answer to the old cross-program scoping request, on all six child groups; it is optional everywhere, so a document holding several programs answers with rows from all of them and nothing errors.
An `--address` filter keeps exact-start-match semantics — it selects rows that *begin* at that address, so `segment fetch --address @1000006E8` returns nothing while `addr @1000006E8` says the address is inside `__TEXT`. Only `addr` asks "what contains this"; a `--address` given as a name or an `off:` is resolved against one program, so with several programs in the document it needs `--binary` too.
Inserts take the same vocabulary positionally: `symbol insert <binary> <name> <address>`, `section insert <binary> <segment> <name> <address>`, `procedure insert <binary> <symbol>`, `annotation insert <binary> <address> <text>`, `bookmark insert <binary> <name> <address>`, `segment insert <binary> <name> <address>`.
`procedure insert` resolves its symbol by name **or** identifier, and `section insert` / `segment insert` resolve their parent before writing, so a typo exits with `unknownSegment` / `unknownSymbol` / `unknownBinary` instead of attaching a row to the wrong parent.
Duplicate guards exist only where the schema has a `#Unique` key: `segment` [`binary`,`address`], `section` [`binary`,`address`], `symbol` [`binary`,`address`,`identifier`], `procedure` [`symbol`].
`annotation insert` and `bookmark insert` have no guard, because neither model declares a unique key, so re-inserting the same row duplicates it.
`program` has no `insert` deliberately: `import` is the only creator of `BinaryModel` rows.
The cascade census is scoped by exactly the same filters, because it counts the rows the delete selected rather than the document: on the `big` store `symbol delete --dry-run` answers `Deleted 15052 symbols — left behind 8903 procedures pointing at a deleted symbol`, while `--limit 100` answers `Deleted 100 symbols` with no clause at all — none of those 100 lowest-address rows is a procedure's symbol — and `--address @1000014F0` (a procedure symbol from `procedure fetch big`) answers `Deleted 1 symbols — left behind 1 procedures pointing at a deleted symbol`.

### Gotchas verified at runtime

The one working SwiftData filter shape unwraps the optional **outside** the predicate: `let text = options.text.flatMap { filter in #Predicate<AnnotationModel> { $0.text.localizedStandardContains(filter) } } ?? .true`, and the parts are then composed with `descriptor.predicate = #Predicate<M> { a.evaluate($0) && b.evaluate($0) }`.
The tempting variant that keeps the `flatMap` inside the macro compiles and then aborts the process — `CoreData: error: … can't use NULL on left hand side`, `*** Terminating app due to uncaught exception 'NSInvalidArgumentException'`, `Abort trap: 6` — for every `fetch`, `count` and `delete` in every group.
`&` is rejected by the macro (`The '&' operator is not supported in this predicate`), so `--flags` and `--protection` are exact-equality filters and no bitmask filter is expressible at all.
Only stored fields may appear in a predicate: `SymbolModel.kind` / `.type` / `.binding` are computed over `rawKind` / `rawType` / `rawBinding`, which is what the filters compare, and `SectionModel.isExecutable` / `isZeroFill` / `containsCode` are computed too — which is why those three print but cannot be filtered.
Relationship keypaths do translate: `$0.binary.name`, `$0.segment.name`, `$0.symbol.name`, `$0.symbol.address`, and `SortDescriptor(\ProcedureModel.symbol.address)` works.
SwiftData adds a `Predicate`-based `filter` overload that wins overload resolution on a model array, so `program.procedures.filter { $0.contains(address: address) }` does not take the closure — it fails with `initializer for conditional binding must have Optional type, not '(Predicate<ProcedureModel>) throws -> [ProcedureModel]'` (and `missing argument label 'by:'` for `.max({ … })`). Code outside a `#Predicate` that walks model collections — `Addr.swift`'s owning symbol/procedure probes — has to use `for … where` accumulator loops instead of `filter` / `max` / `sorted`.
Address notation is chosen by the shape of the token, and that has two sharp edges verified at runtime: a bare all-decimal token is always a virtual address, so a symbol whose name is all digits cannot be selected by name; and name lookup is exact over `name` / `identifier`, so `addr <proj> main` on `thin_test` exits `No symbol named main in thin_test` because the row is `_main`. The `localizedStandardContains` fuzziness of `--name` was deliberately not carried over, because an address argument feeds writes as often as reads. `--address 4294969064`, `--address 0x1000006e8`, `--address @1000006E8` and `--address _main` all select the same row.
The `off:` prefix and `addr`'s `off=` field resolve through the segment table (`fileoff` / `vmaddr` per load command), which is the right answer, and `bytes` reads through the same primitive: `fileOffset(of:in:)` in `Sources/Utilities.swift` picks the segment with `fileSize > 0` that covers the address and adds the delta. AetherKit's own `BinaryModel.load(_:at:)` / `span(at:)` / `read(at:count:)` / `data(in:)` / `format(hex:)` helpers in `Schema+.swift` still shift by `baseAddress` alone, so the CLI deliberately does not use them; on a binary whose segments are not one contiguous `fileoff = address - baseAddress` block they would read from the wrong place while `addr` reports the right one. Fixing the helpers, not papering over it in the CLI, is the honest option, and entry 4's `find` should reuse `fileOffset(of:in:)` rather than inventing a third mapping.
`bytes`'s `segment=` can name `__PAGEZERO`, whose `size` (`0x1_0000_0000`) spans the whole preferred-base void: `addr <proj> @1000C000` prints `segment=__PAGEZERO prot=--- off=none`, which is true of memory but not of the file. The read side is stricter — the offset lookup demands a segment with `fileSize > 0`, so `bytes <proj> @1000C000` exits `Error: Virtual address @1000C000 is not inside any segment of thin_test`. Zero-`address` rows are excluded the same way: an imported symbol is stored at `0` with `size == 0`, and the owner probes now skip them, so no row pretends to own every address. The procedure probe has the mirrored weakness — a code procedure with `size == 0` runs to the end of its section and beyond, so `addr <proj> @100004010` (a `__DATA_CONST,__got` address) answers `procedure=stub_100000AC0`.
A run that hits the end of the file is reported, not silently truncated: the header prints `bytes=8 asked=64` and one short row, a typed read prints the values it got first and then exits `Read ran past the end of thin_test's file data at @10000C918: 1 of 4 values`, and an address with no file bytes behind it exits `Nothing to read at @…: file offset … is past the end of thin_test's file data`.
`--as` has no signed or 128-bit kinds: `ptr` takes its width from `is64` (8, or 4 for a 32-bit program) and every multi-byte read takes its byte order from `endian`, whose only cases are `.little` and `.big`. `cstr` / `wstr` stop at their terminator and are capped at 512 units when nothing terminates them, a trailing ` …` marking that the cap was what stopped the read; invalid UTF-8 falls back to one character per byte rather than failing the read. Strings are escaped (`\n`, `\u{…}`) because a byte inside a string would otherwise break the one-row-per-line invariant entry 7 is about.
An `off:` outside every segment of the program exits `File offset 3B9AC9FF is not inside any segment of thin_test`; a name that matches several addresses exits `… resolves to several addresses in thin_test: … — pass an address instead`; several programs with no `--binary` exits `Several programs in the project — pass --binary: …` rather than guessing one.
`find` finds hits by file offset and maps them back with `virtualAddress(of:in:)`, the inverse of `fileOffset(of:in:)` over the same segment table. That is honest about bytes and generous about meaning: the Mach-O header lives in `__TEXT`'s file range (`fileoff = 0`), so `find --pointer-to _main` hits the header's own `entry` field at `off=D0 @1000000D0 segment=__TEXT section=none`, and an address nothing is symbolized at. Pointer hits are scanned at every byte offset, which is why the row carries `aligned=true|false`; the loader's own tables (the header `entry`, each section's `addr`) are real hits, which is what makes this the *primitive* xref pass rather than the analyzer's answer.
`--bytes` normalizes its pattern — `ff??02` reports as `FF??02` — and a bad one (`ZY`, an odd length) is an invalid value at exit 64 rather than a symbol lookup, since there is nothing else `--bytes` could mean. `--text ''` exits `--text cannot be empty, it would match every byte in the file` and `--pointer-to 0` exits `Nothing points at address 0: it is not inside any segment`; both needles would otherwise match the whole file. A run with no hits prints `No hits in thin_test` and exits 0, unlike `grep`, because one invocation may run several patterns.
A digest is a computed value, so nothing can filter on one: `describe()` prints `sha256=` but `#Predicate` sees only stored fields, which is why the corpus dedupe has to be a scan in `aether-cli` (`hash` over one `<project>` at a time) rather than a filter. The SDK spells MD5 `CryptoKit.Insecure.MD5`; there is no bare `MD5` in scope. The cost is not the blocker: 256 MiB of SHA256 hashes in 0.12 s (≈2 GiB/s), and `rg`'s 6512544 bytes give all three scopes in 0.06 s, so `program fetch` paying one whole-file pass per row (0.33 s) is noise against the 160 s that program's `import` took.
`body` reports what the file holds rather than what memory would hold: `rg`'s 17 section rows contribute exactly their summed sizes — 4334548 of 6512544 bytes, leaving the header and the sectionless `__LINKEDIT` out — and its three `zerofill=true` rows (`__thread_bss`, `__common`, `__bss`) still contribute bytes because their addresses fall inside `__DATA`'s file range. A section whose segment carries no file bytes is skipped, not zero-padded, and `layout` hashes a text rendering of the section rows, so a rename changes that digest while identical content does not.
`hash --binary Nope` exits 1 with `No program named Nope — this project has thin_test` via `HashError`, because `requireBinary`'s `InsertError.unknownBinary` repr is a leak rather than an answer exactly where the reader needs the project's own program list; an empty project reuses `AddressError.noProgram`, and `--scope zzz` is an invalid value at exit 64 listing `file`, `body`, `layout`.
`InsertError` cases that carry payloads still print as Swift enum reprs — `Error: duplicate(kind: "section", key: "thin_test @1000FE000")` — a thing entry 12's store errors made loud about the store while leaving these reprs alone.
Int-raw enums take their numeric raw value as a CLI argument, so `--format 1` selects Mach-O, `--architecture 3` selects ARM64 and `--endian 0` selects little; the help strings spell the numbering out because the raw-name spelling is rejected.
Under `--dry-run` the mutating commands still print `Inserted …` and `Deleted N <plural>` while persisting nothing, which matches how `import` and `procedure detect` already behaved; the tense of those messages is the papergun, not the behaviour.
Because `count` and `delete` share the filter group, an unfiltered `symbol delete D` wipes every symbol row in the document, and `program delete` cascades to segments, sections, symbols, procedures, annotations and bookmarks — which its own line now says: `Deleted 1 programs — the cascade takes 5 segments, 11 sections, 44 symbols, 14 procedures, 1 annotations, 2 bookmarks`.
The census is asked of the selected rows *before* they are deleted, so `--dry-run` and a real delete print byte-identical lines, and it is read off the relationship arrays of those rows rather than from a query per kind — no predicate can name an instance, so there is no other way to ask "whose children are these". `propertiesToFetch = []` on the delete descriptor does not starve those counts (measured: the line above comes from the same descriptor). Kinds with a zero count are dropped, which is why `references=0` leaves no `0 references` on the end, and the plural-only style `delete` always had is kept, which is why one program's cascade reads `1 annotations`. A kind with nothing below it — `section`, `annotation`, `bookmark` — keeps its bare `Deleted 1 sections` line, because `CascadeReport.describe()` returns `nil` when both halves are empty.
The clause is not free: warm, `program count big` is 0.019 s and `procedure delete big --dry-run --limit 1` (a cascade over one procedure's `blocks`) is 0.017 s, while `program delete big --dry-run` is 0.354 s and `symbol delete big --dry-run --limit 1` is 0.170 s, because those walk 15052 symbol and 8903 procedure relationship entries. That is the same order as the rows the delete is about, and it is the work `program fetch` already pays 0.34 s for when `describe()` prints those same counts, so the cost is proportional and not new in kind — but a delete of a huge program now costs roughly that much even under `--dry-run`.
`left` exists because the schema's one required to-one declares no delete rule: `ProcedureModel.symbol: SymbolModel` (`Schema.swift:193`) says nothing about the reverse direction, so deleting symbol rows leaves procedure rows alive and counted. Measured with a real delete on a copy of j7 — `symbol delete ../.qwen/tmp/symdel15.aetherproj --address @1000006E8` prints `Deleted 1 symbols — left behind 1 procedures pointing at a deleted symbol` — and afterwards `symbol count` is 43, `procedure count` is still 14, `symbol fetch --name _main --all` answers `Showing 0 (0-0) of 0 symbols:`, and the next `procedure fetch` prints its `Showing 1 (1-1) of 14 procedures:` header and then dies inside SwiftData: `SwiftData/BackingData.swift:1145: Fatal error: This model instance was invalidated because its backing data could no longer be found the store. PersistentIdentifier(… SymbolModel/p7 …)`, exit 133. So the ghost rows are not untidy bookkeeping, they are a trap already written into the document, which is why the count line reports them *before* the delete happens. Over `big` the same rule reads `Deleted 15052 symbols — left behind 8903 procedures pointing at a deleted symbol`: an unfiltered symbol delete orphans the entire procedure table.
`procedure delete` prints no clause for a reason that is not the code: nothing in the repo constructs a `BlockModel` (`BlockModel(` has no call sites anywhere in `Aether/`, `AetherKit/` or `aether-cli/`), so `ProcedureModel.blocks` (`Schema.swift:199-200`, `deleteRule: .cascade`) is always empty and its `cascade` can only ever return an empty report until blocks are populated by something.
The census describes what *this* delete will do, not damage already in the store: on `.qwen/tmp/sym15.aetherproj` — j7 with `_main`'s symbol row deleted by hand earlier, 43 symbols and 14 procedures — `symbol delete --dry-run --limit 1` walks all 14 procedure rows, matches none of them and prints `Deleted 1 symbols` with no clause. The pre-existing ghost is invisible to it, and reading `persistentModelID` off the invalidated `symbol` relationship does not trap, which is what lets the walk survive an already-corrupted store; the only thing that surfaces that damage is the `procedure fetch` trap above.
`import --replace` selects the programs to clear by `name == url.lastPathComponent` through a predicate on `name` (reading `name` back off every program instead would drag each program's whole `data` blob out of external storage to decide a match), and `name` is **not** unique in the schema — so on a copy of `.qwen/tmp/two.aetherproj`, which holds two `BinaryModel` rows both named `thin_test`, it clears both: `Deleted 2 programs — the cascade takes 10 segments, 22 sections, 66 symbols`, after which `program count` is 1. That is what the duplicate-store corpus wanted and it is also a footgun for a document that holds same-named programs on purpose. The delete runs before the parse but is only *reported* after it, because the command keeps its single `save()` at the end: `import --replace ../.qwen/tmp/repl15.aetherproj ../.qwen/tmp/notmacho.txt` exits 1 with `Error: Not a Mach-O binary (magic 0x6c6c6568 — not a Mach-O header)` and prints **no** `Deleted` line, leaving the store's 1 program and 42 symbols intact, while `--dry-run --replace` prints the clause and persists nothing (`program count` afterwards is still 1). A real round trip re-parses in place instead of appending: two consecutive `import --replace ../.qwen/tmp/repl15.aetherproj ../.qwen/tmp/thin_test` leave `program count` 1, `section count` 11 and `symbol count` 42, the second command's row printing `symbols=42` exactly like the first.
The default 100-row page lives in `FetchOptions.pageLimit()` rather than inside `apply(page:to:)` for exactly that reason: `symbol delete --dry-run big` still reports `Deleted 15052 symbols — left behind 8903 procedures pointing at a deleted symbol`, while `--limit 3 --dry-run` reports 3 and `--all` is a no-op there — a delete never had a page to lift. On the read side `symbol fetch big` prints `Showing 100 (1-100) of 15052 symbols:` then `… 14952 more — --all for every row, --offset 100 for the next page`, the whole census taking 0.66 s against the page's 0.04 s in a debug build (0.46 s and 0.03 s in release), so the win is a readable terminal rather than speed. `--all` outranks a typed `--limit` rather than erroring, which is what `find --all` already does with its own 500-row default, and `--demangle`'s census counts the page, not the result: `symbol fetch big --demangle` says `demangled 0 of 100 rows — neither /usr/bin/swift demangle nor /usr/bin/c++filt recognised these names`.
A zero page has to be answered before the fetch rather than handed to the descriptor: SwiftData reads a zero `fetchLimit` as "no limit", so `symbol fetch big --limit 0` used to print the whole 15053-line census. It now prints `Showing 0 (0-0) of 15052 symbols:` — `find --limit 0`'s "counts without printing" — and `[]` under `--json`. A negative page gets the typed error `find` answers with (`--limit=-1` exits 1 with `Error: --limit cannot be negative`), though the bare `--limit -1` never reaches that check: ArgumentParser replies `Error: Missing value for '--limit <limit>'` at exit 64.
`symbol raw`'s three bucket sections page through the same default, which is where the win is largest: rg's report went from 765 lines (`--all`, 1 m 38.9 s release) to 107, the stale bucket printing `stale — stored rows the current loader no longer produces: 759, showing 100` plus `… 659 more — --all for every row, --offset 100 for the next page`. Its `--json` branch is untouched because that report prints only counts, and `symbol count` after the run is still 15052 — the scan still writes nothing.
The `Showing` range is now 1-based inclusive — `--limit 7` gives `Showing 7 (1-7) of 15052 symbols:`, `--offset 100 --limit 2` gives `Showing 2 (101-102) of 15052 symbols:` — where it used to be half-open against a total that is not, so one row printed `Showing 1 (0-1) of 1 symbols:` and read as two. An empty page still prints `Showing 0 (0-0) of 0 <plural>:`, which is why the `--section __DATA,ZZ` measurement further down still reads `Showing 0 (0-0) of 0 symbols:` while the one-row `--section __cstring` case moved to `Showing 1 (1-1) of 1 symbols:`.
A document written by the pre-conversion build still refuses to open, and it now fails instead of trapping: measured on the fixture `.qwen/tmp/clidocs/ThinTest.aetherproj`, every command exits 1 with `Error: Cannot open the store at <abs path>: The operation couldn't be completed. (SwiftData.SwiftDataError error 1.) — a store written by an older model list is the usual cause`. That message carries **no reason at all** — SwiftData hands back an opaque `SwiftDataError error 1` — while the clauses that do explain it are printed by SwiftData itself on stderr, 280 251 bytes of CoreData schema dump containing `Code=134140 … reason=Can't find or automatically infer mapping model for migration` and `Code=134190 … entity=BinaryModel, property=format.format, reason=Source and destination attribute types are incompatible`. So a script greps that dump for `property=` rather than reading the error line, and this file's earlier note naming `endian.endian` blamed the wrong attribute: the property that trips first is `format.format`. The scratch corpus of older `.aetherproj` stores is still dead to the current build rather than merely stale; what changed is the exit code, 133 → 1, and the fact that a script can now tell "this store is unopenable" from "this store is empty".
`--existing` is the opt-out of create-on-demand, and it is a path check rather than a schema check: `program count --existing <typo>` exits 1 with `Error: No project at <abs path> — --existing does not create one` and leaves nothing behind (verified: the bundle does not exist afterwards), while the same command without the guard prints `0`, exits 0 and creates the `.aetherproj` directory plus its `StoreContent`. A bundle that exists but whose store cannot be migrated is not caught by `--existing` — it reaches the `Cannot open` path above. `doctor` is not exempt from the default either: it opens the store like any other command, so diagnosing a typo'd path creates an empty document (`doctor ../.qwen/tmp/fresh12.aetherproj` created it and then reported `programs=0`) unless `--existing` is passed. Only `inspect` lacks the flag, because it takes no project at all.
`doctor`'s containment line only reads sensibly because address 0 is counted separately: imported symbols are stored at `0` with no size, so j7 prints `13 at address 0` rather than calling them all offenders, and its one genuine row is `__mh_execute_header @100000000 size=1768 … export=true` — the file's own prefix, which no section covers. Nothing disambiguates programs that share a name: `.qwen/tmp/two.aetherproj` holds two `BinaryModel` rows both named `thin_test`, so its two blocks print byte-identically while the census line says `programs=2`.
The histograms agree with the `symbol count` census case by case — on j7 `--kind` gives `15 / 14 / 15 / 0` for unknown/function/data/section, `--type` gives `29` unknown, `1` ascii, `14` function and `0` for the other seven, `--binding` gives `2 / 27 / 2 / 0 / 13` — and they cost no query because they ride inside the containment walk `doctor` already performs. Zero counts are dropped from the printed line, which is why a `--kind section` census of `0` has no `section:0` to match on the other side of the dash, and a program whose rows are all deleted prints no histogram line rather than three empty ones.
The `untyped` tell is only reachable through rows the CLI made by hand: the current loader types every row it writes, so measuring it takes a hand-built store (`.qwen/tmp/ut17.aetherproj`, whose two rows carry no kind, type or binding). That store is exactly the trap the tell exists for — containment reads clean (`2 symbols over 11 sections — 2 inside a section, 0 at address 0, 0 outside one`) — and `--strict` there exits 1 on `untyped` alone with `outsideSections=0`.
`--strict` fails by throwing `ExitCode(1)`, the one error ArgumentParser exits on without printing an `Error:` line, which is what lets `--json` differ from a plain run only in status. It counts rows rather than programs — every outside row plus one per untyped program — so the status and the printed report cannot disagree about what was found. The measured fact is uncomfortable: **every store the current loader writes fails it**, because every Mach-O program carries `__mh_execute_header @100000000 … export=true` outside every section (size 1768 on j7, 5360 on rg), and both `doctor ../.qwen/tmp/j7.aetherproj --strict` and `doctor ../.qwen/tmp/big.aetherproj --strict` exit 1 on that single row. That is a true finding rather than a false positive, and exempting it would make the exit code disagree with the containment line, so a script wanting a usable gate greps the offender rows instead; the flag's uncontaminated uses are the hand-made untyped store (exit 1) and a store with no program or no symbol rows (exit 0).
`--version` is accepted by **every** subcommand, not only the root: ArgumentParser adds the flag to any command whose stack contains a version, so `symbol fetch ../.qwen/tmp/big.aetherproj --version` prints `1.0` and exits 0 instead of any rows, and every `--help` gains `--version   Show the version.`. `cli=1.0` in the census names the build doing the reading, not the build that wrote the store — which is precisely the half entry 17 still cannot answer without a stamp inside the document.
A `ModelContainer` with no `configurations:` does not mean "in memory": it opens `~/Library/Application Support/default.store`, which is why `AetherTests`' `ModelContainer(for: Schema.project)` fails on that stale file. The in-memory shape is `ModelConfiguration(schema:isStoredInMemoryOnly:)` — there is no `inMemory:` label, and `url:` is a separate initialiser, so a store path and in-memory storage cannot be combined in one configuration.
Every JSON value is a string — `"count": "44"`, `"size": "1"`, `"align": "4"`, `"thunk": "false"` — because one `fields()` list feeds both renderings and the text row has no numbers to be typed; a script parses the number itself. Compound values stay compound rather than fanning out into sub-keys: segment `file` is the one field `"0+4000"`, procedure `arguments` / `locals` are the bracketed lists the text row prints, and bookmark `created` is a date with spaces.
Control characters are escaped in both renderings, which is the fix for the entry's papergun rather than only for JSON: a symbol inserted with `--value $'x\ny'` now prints `… identifier=nl_test value=x\ny program=thin_test` on one line (`symbol fetch --name nl_test` is 2 lines where the row used to wrap into 3) and `"value": "x\ny"` under `--json`. `RowField` carries the raw `value` and the escaped `text` separately, so JSON escaping is a second pass that additionally protects the two characters JSON cannot carry — `"summary": "quote \" and \\ back"` round-trips through `python3 -m json.tool` from an `insert --summary 'quote " and \ back'`. Note Swift has no `\b` / `\f` string escapes: the escaper spells those cases `"\u{08}"` / `"\u{0C}"`, and the naive literals fail with `invalid escape sequence in literal`.
Two things `--json` still cannot do. A field selector is absent, so getting one value out of a row means parsing JSON (`program fetch --entrypoint --bare` is still impossible), and a JSON consumer gets no paging information at all — neither the `Showing N (lo-hi) of M` header nor the `… N more` line is printed, which is precisely why the 100-row default page is not applied under `--json`: an array that stopped early would have nothing to admit it. The rows themselves are unambiguous in JSON and not in text: `annotation`'s head field is free text (`entry point @1000006E8 kind=inline`) and `bookmark`'s `created=` value contains spaces, so a `key=value` line cannot be re-split into fields without the JSON view.
`--section` cannot compare a stored field, because a `SymbolModel` has no relationship to a `SectionModel` — which is why sections are their own group while symbols do not scope to one. `filterSection(_:named:in:)` (`Sources/Utilities.swift`) resolves the section first and the predicate becomes `$0.address >= lo && $0.address < hi` over two captured `UInt64` lets, since the predicate compiler only ever sees plain comparable values here and not a `Range<UInt64>`. Matching is exact, like every other name that selects a place rather than searching a label, and both spellings work: `--section __cstring` and `--section __TEXT,__cstring` both give `Showing 1 (1-1) of 1 symbols:` with the one `str_100000B00 … size=21 … type=ascii` row. The three failure paths are a typed `SectionError` rather than a `#Predicate` because the disambiguation is a lookup, and all three exit 1: `Error: No section named nope in thin_test`; `Error: Several programs in the project — pass --binary: thin_test, thin_test` (a section needs one program, so `--binary` is mandatory there); and the same name in two segments of one program is refused rather than guessed — `Error: ZZ is several sections in thin_test: __TEXT,ZZ __DATA,ZZ — spell it as <segment>,<section> instead`, measured on a store holding `section insert T thin_test __TEXT ZZ @100003C00 --size 32` and its `__DATA` twin, where `--section __DATA,ZZ` then resolves (and legitimately answers `Showing 0 (0-0) of 0 symbols:` at exit 0, because that hand-made section covers no symbol).
`symbol raw` is built around one fact about the loader: `MachOLoader.symbolize(in:)` is **not idempotent**. Its "named" skip set is every stored symbol with `address != 0 && size > 0` — `overlapsNamed` per element, `hasNamed` for the section-spanning row — so re-scanning an already symbolized program emits *nothing* and every generated row then reads as stale; measured during development on a store holding 7 generated rows, scanning that program in place gives 0 rows and the report says `missing 0 stale 7 changed 0`. A hand-built copy of the program does not dodge it either: the rows a model's initialiser attaches (`SegmentModel(in:)`, `SectionModel(in:of:)`, `SymbolModel(in:)`) are only kept for a model its store tracks, so a detached `BinaryModel` clone comes back `segments=0 sections=0 symbols=0` and there is no way to rebuild a program graph outside a store. The re-parse therefore runs against the stored bytes in `ModelConfiguration(schema: .project, isStoredInMemoryOnly: true)` — `inspect`'s store — which is also why `raw` can promise it writes nothing: the opened container is never touched, and `symbol count` after a `raw` run is unchanged (15052 before and after on the `big` store).
A `BinaryModel.data` read back out of a store is not a plain `Data`. SwiftData hands `@Attribute(.externalStorage)` bytes back as a view into a memory-mapped buffer whose start is **not** 8-byte aligned, and `MachOLoader.machO(for:)`'s first act is `bytes.unsafeLoad(as: mach_header_64.self)`, so passing the view through traps with `Swift/UnsafeRawPointer.swift:450: Fatal error: load from misaligned raw pointer` — `💣 Program crashed: System trap`, exit 133. `raw` re-copies first (`program.data.subdata(in: 0..<program.data.count)`), and that copy is what makes the re-parse run at all. The same trap should be reachable anywhere a model's `data` comes back from the store instead of from a file — the app's "Load..." on a reopened document is the obvious one, which is inference rather than something measured here — making it a loader-side bug the CLI only works around: `readUInt32LE(at:)` and friends in `Schema+.swift` do unaligned reads, the header load does not.
"what the current loader would produce" is two questions, not one, because the detector appends symbol rows of its own: `Analysis/ProcedureDetector.swift:225-229` creates a `SymbolModel` per synthesized entry point named `sub_<address>`, or `stub_<address>` for a dyld-call stub, and appends it to `model.symbols`. Parse-only `symbol raw j7` reports `missing 0 stale 11 changed 0` with nine of the eleven being `stub_100000A60` … `stub_100000AC0`; the same store under `--analyze` reports `42 of 42 re-parsed rows` and `missing 0 stale 2 changed 0`, those two rows being the hand-inserted `nl_test` / `q_test` — i.e. the only genuine drift. So the flag is not a detail: a report that conflates "the loader changed" with "detection was skipped" is worse than no report, which is why skipping detection prints a line saying so and `--json` carries `"analyze": "false"`. On the `big` store the flag is the whole story: parse-only reports `14293 of 14293 re-parsed rows, 15052 of 15052 stored rows` with `missing 0 stale 759 changed 0`, while `--analyze` reports `15052 of 15052` and `missing 0 stale 0 changed 0` — that store is reproduced exactly by the current pipeline, and all 759 rows were detector rows.
The re-parse costs what inserting into a store costs, not what parsing costs: on rg's 6512544 bytes `symbol raw --json` takes 1 m 40.6 s in a release build and 1 m 42.1 s in a debug one — so optimisation is not the lever — and `--analyze` takes 2 m 34.6 s, against the 160 s that program's `import` took; `thin_test` is 0.023 s. That is structural rather than a missing optimisation, because the scan cannot run against anything but a store.
`--demangle` routes a name onto the toolchain's own demanglers by prefix rather than trying to speak a mangling grammar: `/usr/bin/swift demangle` gets names starting `_$` or `$`, `/usr/bin/c++filt` gets names starting `_Z` or `__Z`, and nothing else is fed to either tool. Names cross **verbatim**, with no underscore stripped — `c++filt` demangles the double-underscore spelling `nm` prints (`__ZN2ns6Widget6renderEiPKc` → `ns::Widget::render(int, char const*)`), so stripping would corrupt a plain `_main` into `main` as well as misroute it, and `_main` is left alone in the same run that demangles its neighbour. `swift-demangle` is not on `PATH` on this machine, which is why the CLI shells out to `swift demangle`. A whole page goes through one process per tool, fed as a temp file on stdin — `Process` cannot hand a child a string, and both tools read an argument as a *file name* — and the answers are paired back by position, so a tool printing a different line count from the names it was given is not applied at all rather than guessed row by row. Measured: 300 names through `c++filt` in 0.007 s, so process start-up is the only cost worth paying and a page of any size is still at most two processes; on the rustc store both batches come back empty and neither tool is launched — `symbol fetch --demangle --limit 3` takes 0.073 s and prints `demangled 0 of 3 rows — neither /usr/bin/swift demangle nor /usr/bin/c++filt recognised these names`, because rustc's current V0 mangling (`__R…`, which is what that store holds) is spoken by neither tool here. A pass-through row prints no field, which is why the census line is the only place text mode can tell "nothing here is mangled" apart from "the demangler failed"; a missing or failing tool earns one line on stderr instead of turning the run into an error.
A row that already carries the column is filled rather than appended to: `procedure fetch --demangle` turns `… leaf=true demangled= blocks=0 …` into `… leaf=true demangled=probe_swift.hello(Swift.Int) -> Swift.String blocks=0 …` at the same position in the row, and a name stored by `procedure insert --demangled` outranks the toolchain's guess, so the column never gains a second value to disagree with. `symbol` rows have no such column and gain a trailing `demangled=…` only when a demangler changed the name. Swift's demangler also answers import rows — `_$sytWV` → `value witness table for ()` — so the census counts rows, not distinct names. The naming trap worth recording: a protocol member spelled `row(demangled:)` was not available, because the call resolves to a member taking a single `String` before it reaches `FetchableModel` and fails as `cannot convert value of type '[String : String]' to expected argument type 'String'`; hence the `applying:` label.
`snapshot` pins **all seven** groups rather than the three the entry names, and pins the program row's per-kind counts too — which is why a one-symbol insert shows up twice on `big`: `Differences: 2 of 23978 pinned rows — 1 added, 1 changed` with `changed program rg — symbols 15052 -> 15053` above `added symbol marker_22 @100000000`. The discriminator field is `group`, not the obvious `kind`, because `symbol` rows already carry a `kind` column and overwriting it would drop the distribution entry 17 reports. That field is also the file's only validity check, and it is a check rather than a hope: a `program fetch --json` dump decodes as `[[String: String]]` perfectly and would otherwise report every row of a real store as both gone and new, so `changes j7.aetherproj dump22.json` exits 1 with `Error: Cannot read the snapshot at dump22.json: a row has no "group" field — it has to be a file written by \`snapshot\`, a JSON array of objects of strings`.
The file is deterministic rather than merely JSON: rows are sorted group → program → name → address → row, so two runs over one store write byte-identical bytes (`cmp` clean on both runs against `snap22.aetherproj` and on rg's 23978-row store), and a run whose stdout is redirected writes the same bytes as `--out` — a mismatch here was real and silent, `print` adding a trailing newline that `write` did not, caught as `cmp: EOF on .qwen/tmp/big22b.json`. A hand-edited file still diffums: four `size` fields changed by hand in a copy of j7's snapshot read back as `changed section __DATA_CONST,__got — size 105 -> 104` etc., folded into the mutation diff of the same file as `Differences: 8 of 78 pinned rows — 1 added, 1 removed, 1 renamed, 1 moved, 4 changed`, and the direction is file → store throughout; the reader rebuilds each row's fields in key order rather than expecting the store's order. Neither command filters or selects: the diff is whole-table, so a file pinned from another project reads as every row gone — `changes` on j7 against rg's snapshot printed `Differences: 24056 of 23978 pinned rows — 78 added, 23978 removed`, more differences than there were pinned rows, at exit 0 until `--fail-changed` says otherwise. A store with no rows reads the same way against a real file: `Differences: 78 of 78 pinned rows — 78 removed`, which is what a typo'd project path still looks like here unless `--existing` is passed — the create-on-demand trap entry 12 made loud, arriving as an honest diff of an empty store rather than an error.
The five kinds were measured together on one mutated store: `Differences: 5 of 78 pinned rows — 1 added, 1 removed, 1 renamed, 1 moved, 1 changed`, whose lines are the five quoted under the surface section above. A rename only appears at all if the rest of the row agrees, which is why the test inserted `my_data` at the address of the deleted `DAT_100000B18` rather than renaming anything — the store has no rename command, and a row whose fields did not agree would correctly have been reported as two edits. `--fail-changed` exits 1 on that store and 0 on one that matches, printing nothing beyond the verdict line; `changes` pages like `fetch` (`--limit 2` prints 2 of the 5 differences then `… 3 more — --all for every difference, --offset 2 for the next page`, `--offset 3` the last 2, `--limit 0` the verdict line alone) but prints no `Showing` header, because the total it needs is already in the verdict line.
Two costs worth knowing. `snapshot` is a full read — 0.039 s then 0.024 s on the 78-row store, 1.96 s and a 8 781 075-byte file for rg's 23978 rows — and `changes` pays that read again on top of decoding the file: 0.023 s self-diffed on j7, 2.11 s on `big`, 2.08 s for the one-insert diff that shows the program row's count moving. Neither is free, and neither is the store's fault: `changes` fetches every model twice over, once from the file and once from the document. And it reads every row through `ModelContext.fetch`, so on a store the entry-15 `symbol delete` corrupted it dies exactly like `procedure fetch` does — `snapshot .qwen/tmp/symdel15.aetherproj --out …` is `Trace/BPT trap: 5`, exit 133, `SwiftData/BackingData.swift:1145: Fatal error: This model instance was invalidated because its backing data could no longer be found the store` — which is why a pinned record is not a substitute for the stable identity entry 14 asks for. `--dry-run` is a no-op here rather than a way to skip the write: the flag guards `save()`, and this command saves no store rows, so suppressing the file would leave nothing at all. Both commands reject `--json` at exit 64, which is deliberate for `snapshot` — the file *is* the JSON rendering — and for `changes`, because the row lines are diff descriptions rather than rows.

## Tier 1 — cheap, high value

### 5. `aether procedure detect --explain` — per-pattern census

**Evidence.** `mask_check.py`, `census2.py`…`census9.py` and `sectlist.py` exist purely to measure each detector pattern on its own: per-pattern match counts, true/false positives against objdump labels, per-section hit counts, and imm7/imm9/imm12 extraction sanity (mismatches: 0 of N).
**Status.** `--explain` is still absent, and the reason it is still hard is now measurable: `ProcedureDetectionReport` exposes only the four aggregates (`codeSections`, `entryPoints`, `synthesized`, `created` — `Analysis/ProcedureDetector.swift:22-31`), and `note(_:stackSize:isStub:)` (`:108`) is never told which pattern fired, so a regression in one pattern stays invisible.
**Feature.** Per-pattern counts keyed by the detector's own names (`framePair`, `linkStore`, `stackAdjust`, `bti`, `pacibsp`, `stubThunk`), a per-section breakdown under `--explain`, and `--pattern <name>` to run one pattern.
The scratch scripts' symmetric-diff and mismatches-0 assertions belong in `AetherKit/Tests/AetherTests/ProcedureDetectorTests.swift`, not `.qwen/tmp`.
**Cost.** Medium — thread a per-pattern counter through `note(_:stackSize:isStub:)` and widen the report struct; no schema change.
**Naming to borrow.** borer's `why <binary> <address|name>` — "what is at an address, and where each fact came from" — is the per-address half of `--explain`: the census answers how often each pattern fired, `why` answers which pattern made *this* row. `procedure detect --explain --address <n>` is the same question and is the half a regression test needs.

## Tier 2 — cheap, smaller payoff

### 24. `aether graph` — block CFG and callgraph per procedure

**Evidence.** borer prints both as one-shot text: `cfg <binary> <address|name>` — "function control-flow graph (mermaid)" — and `callgraph <binary> <address|name> [callers|callees]` — "callgraph (mermaid, max 30); `callers` walks what reaches it".
`procedure describe()` already advertises the data with `blocks= callers= callees=`, which print empty for every row today: the rows exist in the store and the CLI has no way to show them.
**Feature.** `aether graph <procedure|address> --format mermaid|dot [--callers <n>]` over a procedure's blocks and its call edges, and `--list-blocks` for plain rows (`startAddress`, `endAddress`, `type`), so the same output feeds `dot`/`mermaid-cli` instead of the app's canvas.
**Cost.** Medium, and cheaper than entry 4's xrefs: `BlockModel.startAddress` / `endAddress` / `type` / `successors` / `predecessors` are already `public` in `Schema.swift`, and the walk starts at `ProcedureModel.blocks` (public, `deleteRule: .cascade`), so nothing has to be added to `Array<any PersistentModel.Type>.project` (`Schema.swift:4`) — no migration, which is what entry 12/17 keep tripping over.
Two real gaps. `BlockModel.procedure` / `init` are internal, so block rows must be reached through their procedure rather than fetched; and `ControlFlowStructurer` is internal throughout (`nonisolated final class` at `Analysis/ControlFlowStructurer.swift:19`, `func structure(procedure:instructions:)` at `:153`, `struct CFGBlock` at `:8`), so this command can print the stored CFG but not the recovered if/while/switch shape until that visibility changes.
`BasicBlockType` is `String`-backed (`Schema/Arch.swift:149`: entry/normal/exit/conditional/loop), so `--type Loop` needs another `@retroactive ExpressibleByArgument` in `aether-cli/Sources/AetherKit+.swift` — and unlike the `Int`-backed enums it will parse by raw name, not by number.
Filtering blocks by type is a post-query decision, not a predicate: `BlockModel` is not a fetchable group, and `type` is a stored field only on a model no descriptor is built for.

## Tier 3 — real work, keep separate

### 13. `aether disassemble` — no command, no packaging blocker

**Evidence.** The disassembly ground truth the detector work was measured against is external: `/private/tmp/probe_dis.txt` and `.qwen/tmp/rustc_dis.txt` (68 MB) are `objdump -d` output; `/private/tmp/objdump_labels.txt` is its label list. `aether --help` still lists no `disassemble` command — only the seven model groups, `new` and `import`.
**Cost.** No longer a packaging decision: `AetherKit/Package.swift:16` now pulls `github.com/Lancelotbronner/capstone` (branch `next`) and links `CapstoneKit` into the AetherKit target, and the engine itself has already moved into the package — `AetherKit/Sources/AetherKit/Disassembler/DisassemblerEngine.swift:65` is a `public actor` exposing `disassemble(data:address:architecture:) -> DisassemblyResult` (`:71`), reachable from `aether-cli` with no new dependency. What remains is the command surface: choose a region (a section, a symbol range, or `--address` + `--length`) and print `DisassemblyResult.instructions` / `.pcode`.
**Caveat.** The engine builds its per-architecture disassembler with `try!` (`DisassemblerEngine.swift:78`), so an unmapped `Architecture` traps instead of throwing — a CLI command has to pre-check `architecture.capstoneArch`.
**Region and cap to copy.** borer's `disasm <binary> <address|name> [count]` counts instructions, not bytes — "(default 32, max 256)" — and `disasmfn <binary> <address|name>` walks "a whole function, block by block". So the region selector wants `--count` plus a procedure-name form (entry 21's `<address|name>`), and the cap belongs in the printed output, not only the help.

### 26. `aether decompile` — pseudo-C per procedure, `skeleton` first

**Evidence.** borer's whole pitch is a terminal: `decompile <binary> <address|name> [skeleton|full] [offset] [limit]` — "structured pseudo-C (skeleton: flow and calls only); 300 lines a page, a limit past the last line for all" — which is how a 15795-procedure binary is readable at all: `skeleton` costs one structuring pass per function and answers "what does this call and where does it go" without printing the body.
**Feature.** `aether decompile <procedure|address> [--skeleton] [--offset <n>] [--limit <n>]`, printing `Decompiler`'s text for one procedure; `--skeleton` = control flow plus call sites only, and paging consistent with entry 23 so a 3000-line function does not flood a script.
**Cost.** Lower than expected: the decompiler is already in the package — `AetherKit/Sources/AetherKit/Decompiler/Decompiler.swift:93` is `public func decompile(procedure: ProcedureModel, instructions: ArraySlice<DisassembledInstruction>, binary: BinaryModel) -> String` on a `public nonisolated final class Decompiler`, reachable from `aether-cli` with no new dependency.
What is missing is feeding it: `DisassemblerEngine.disassemble(data:address:architecture:) -> DisassemblyResult` for the procedure's address range, sliced to `ArraySlice<DisassembledInstruction>`, and `ProcedureModel` rows — so entry 16's `analyze --pass` is the prerequisite for re-checking one function after an edit, and entry 13's `try!`-trap caveat applies verbatim.
Still Tier 3 on merit: nothing in this repo has measured `Decompiler`'s output on the rustc corpus, and it keeps its own `ControlFlowStructurer` privately, so a `--skeleton` flag means teaching `Decompiler` to stop after structuring rather than picking a cheaper path.

### 27. `aether grep` — render the program once, then search it

**Evidence.** borer pairs the two halves deliberately: `index <binary>` — "decompile every function once into the cache that grep reads" — then `grep <binary> <text> [filter] [offset] [limit]` — "pseudo-C lines containing the text program-wide, or matching it when written `re:<expression>` (`(?i)` inside ignores case); filter names the function (100 a page, max 500)". The cache is what makes the second question cheap.
The scratch set needed it: `objdump_labels.txt`, `aether_procs.txt` and the 68 MB `rustc_dis.txt` greps were the tool for finding which procedures reference a constant or a string.
**Feature.** `aether grep <text> [--procedure <name>] [--regex re:<expr>] [--lines <n>]` over every procedure's rendered disassembly / p-code, printing `<address> <procedure> <line>`; `aether index` as the pass that builds the cache, and `--procedure` as the filter borer's "filter names the function" implies.
**Cost.** High, and it is entry 13 + entry 26 first: rendering over all `ProcedureModel` rows means one `DisassemblerEngine` call per procedure, and that engine is an `actor`, so the pass is sequential — 15795 procedures on the rustc document.
`#Predicate` cannot express any of it: nothing in `Schema.swift` stores rendered text, computed properties may not appear in a predicate at all, and even the `--procedure` narrowing has to unwrap outside the macro the way the gotchas section documents.
A cache therefore means either a new stored column on `ProcedureModel` (a schema change, and with it the migration hazard entries 12/17 keep hitting) or an on-disk sidecar outside the store like borer's index — the second avoids the migration risk and is the reason not to reach for a model first.

## More gaps — measured against the scratch stores rather than the scripts

### 16. `aether analyze` — re-run a pass without re-parsing

**Evidence.** The detection pass is welded into the loader at `Load/MachOLoader.swift:174` (`let report = ProcedureDetector().detect(in: model)`) inside `machO(for:)`, so re-analysing a stored document once meant re-importing it; the five `rustc` documents are the fossil record of that, with counts drifting 15795/5981 → 10712/7547 → 10712/7546 → 14881/11716 for one identical input. `import --replace` (entry 15) now deletes the program the file's name already matches before re-parsing, so that pile of same-named stores is no longer the only escape — but it is still a fresh parse of the file on disk, which is what this entry is not asking for.
**Feature.** `--list-passes` and the general `analyze --pass <name>`: detection is the only pass reachable from the CLI and `machO(for:)` still calls it inline, so a second pass has no name to ask for.
The report still says nothing about the `SymbolModel` rows the passes insert — a fresh `thin_test` import lands 42 symbol rows from a run that narrates 33 — so the census a script sees depends on which passes have run. Pass-aware counts in every report is the fix.
**Caveat.** Re-running is safe: `ProcedureDetector.detect` is append-only and `ProcedureModel` carries `#Unique<ProcedureModel>([\.symbol])` (`Schema.swift:190`).
**Naming and a report shape to copy.** borer's `index <binary>` ("decompile every function once into the cache that grep reads") is exactly what `--pass <name>` needs: a named, re-runnable, idempotent pass with a sidecar artefact rather than a loader side effect.
Its `triage <binary>` — "one call: what it is, what it hides, where to read" — is the aggregate every pass should leave behind: one block naming the format, the protection facts, the counts by model and the addresses worth reading first, so entry 1's `inspect` and entry 16's `analyze` print the same report.

**Feature.** What is still missing on `aether doctor <project>`: `schema: stale` for a store that cannot be migrated — saying so instead of failing with an error that carries no reason while the explanation sits in SwiftData's stderr dump — and a version stamp written into the document at `import` time, which is the only way to name the build that *wrote* a store rather than the one reading it. `--strict` and the histograms landed instead of being proposed, and `--strict`'s rule as implemented is "an outside row or an untyped program", not "the store predates the current model list": the second cannot be determined from the rows, so the flag is a verdict on what the report can see and currently fails on every loader-written store's `__mh_execute_header` row.
